# Decisões técnicas

Este documento registra o que escolhi, por que escolhi e o que deu errado no caminho. Decisões maiores têm um ADR próprio em [`docs/adr/`](docs/adr/).

## Arquitetura

- [ADR 0001 — Monólito modular, monorepo e contratos compartilhados](docs/adr/0001-modular-monolith-and-shared-contracts.md)
- [ADR 0004 — Access token em memória, refresh token em cookie httpOnly com rotação](docs/adr/0004-token-storage-and-rotation.md)

Resumo: `backend/`, `frontend/` e `packages/contracts/` num monorepo com npm workspaces. Os schemas Zod do pacote de contratos validam a API, geram o Swagger e validam os formulários do front. As fronteiras entre camadas são regras de lint, não convenção.

## Premissas sobre pontos ambíguos do enunciado

O enunciado deixa alguns pontos em aberto ou em conflito. Para cada um, registro a premissa que adotei e o motivo.

| #   | Ponto                                                                                                                                                                                             | O que assumi                                                                                                                                                                                                                                                                                                                                                                                                  |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | O `api-spec` devolve o `refreshToken` no corpo, mas os critérios eliminatórios reprovam token acessível ao front sem httpOnly                                                                     | Mantenho o contrato do spec (o `refreshToken` vem no corpo e o `/refresh` o aceita no corpo) e, além disso, gravo o refresh token num cookie `httpOnly; Secure; SameSite=Strict`. O front nunca lê o token do corpo nem o guarda em storage acessível por JavaScript: renova a sessão só pelo cookie, e o access token fica em memória. Clientes de API (Swagger, curl, testes) usam o contrato exato do spec |
| 2   | Produtos indisponíveis "não aparecem nas listagens públicas", mas todas as rotas exigem login                                                                                                     | Não existe listagem pública. O painel mostra todos os produtos; só a seleção de itens de um novo pedido se limita aos disponíveis                                                                                                                                                                                                                                                                             |
| 3   | A tela de pedidos pede filtro por data, mas `GET /api/orders` só filtra por status                                                                                                                | A listagem aceita também `startDate` e `endDate`                                                                                                                                                                                                                                                                                                                                                              |
| 4   | `seed/data.json` não traz datas                                                                                                                                                                   | O seed gera datas nos últimos 30 dias com semente fixa, para que os relatórios tenham conteúdo e os números se repitam em toda execução                                                                                                                                                                                                                                                                       |
| 5   | A regra permite excluir um produto que só aparece em pedidos entregues ou cancelados, mas a FK `order_items.product_id` do schema de referência não tem `ON DELETE`: o banco recusaria a exclusão | Soft delete em produtos (`deleted_at`). O produto some das listagens, a FK continua válida e o relatório de mais vendidos mantém o nome. Pelo mesmo motivo os entregadores também têm `deleted_at`: `orders.delivery_person_id` não tem `ON DELETE`, e o tempo médio por veículo precisa do entregador das entregas antigas                                                                                   |
| 6   | O spec proíbe excluir entregador com pedido `delivering`, mas não define o código de erro                                                                                                         | `409 DELIVERY_PERSON_IN_USE`, no mesmo padrão de `PRODUCT_IN_USE`                                                                                                                                                                                                                                                                                                                                             |
| 7   | "Os relatórios devem aceitar filtro de período", mas `orders-by-status` não tem datas no spec                                                                                                     | `startDate` e `endDate` opcionais também nesse relatório                                                                                                                                                                                                                                                                                                                                                      |
| 8   | O tempo médio de entrega depende do instante da transição para `delivered`, que o schema não guarda                                                                                               | Tabela `order_status_history` com origem, destino, autor e horário de cada transição. Também alimenta a linha do tempo do pedido                                                                                                                                                                                                                                                                              |
| 9   | `PUT /api/products/:id` recebe "todos os campos que serão atualizados"                                                                                                                            | Atualização parcial: só os campos enviados mudam. É o que permite o toggle de disponibilidade direto na tabela                                                                                                                                                                                                                                                                                                |
| 10  | O spec só impede atribuir um entregador que já está num pedido `delivering`. Um entregador atribuído a um pedido `ready` poderia receber um segundo                                               | Regra mais restritiva: entregador com pedido `ready` ou `delivering` está indisponível, garantida por índice único parcial no banco                                                                                                                                                                                                                                                                           |
| 11  | `/auth/refresh` devolve só os tokens; o spec não tem logout                                                                                                                                       | A resposta do refresh traz também o `user`, como a do login: depois de um F5 o front restaura a sessão numa chamada só. Acrescentei `POST /api/auth/logout`, que revoga a sessão, e `GET /api/auth/me`                                                                                                                                                                                                        |
| 12  | O enunciado não diz o que `npm run seed` faz num banco que já tem dados                                                                                                                           | Não faz nada. O container do backend roda migrations e seed a cada start, e um restart não pode apagar o que foi feito pela interface. `npm run seed -- --reset` apaga e popula de novo                                                                                                                                                                                                                       |

## Segurança da cadeia de suprimentos

A regra que segui: nenhuma vulnerabilidade com correção disponível chega à entrega, e o CI reprova se isso mudar. Cada camada tem a sua verificação.

| Camada                 | O que fiz                                                                                                                                                                                                                                                          | Como é verificado                                                         |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------- |
| Runtime                | Node 24.22.1, a primeira versão com a release de segurança de 21/10/2026                                                                                                                                                                                           | `.nvmrc` + `engines` + `engine-strict`                                    |
| Gerenciador de pacotes | npm 11.21.1, última da linha 11 (os advisories mais recentes do CLI afetam até a 11.8.0)                                                                                                                                                                           | —                                                                         |
| Dependências           | Versões exatas (`save-exact`) e lockfile versionado                                                                                                                                                                                                                | `npm audit --audit-level=low` no CI, ou seja, qualquer severidade reprova |
| Instalação             | `ignore-scripts=true` no `.npmrc`. Scripts `postinstall` são o vetor dos worms de cadeia de suprimentos. Só um pacote do projeto tinha script (`unrs-resolver`, ferramenta de lint), e tudo funciona sem ele                                                       | Reinstalação limpa + lint, testes e build                                 |
| Proveniência           | Assinaturas do registry e attestations conferidas                                                                                                                                                                                                                  | `npm audit signatures` no CI                                              |
| CI                     | Actions fixadas por SHA de commit (uma tag pode ser movida); `persist-credentials: false`; permissão só de leitura                                                                                                                                                 | —                                                                         |
| Imagens Docker         | Endurecimento descrito abaixo                                                                                                                                                                                                                                      | Trivy (fixado por digest) no CI, reprovando qualquer CVE corrigível       |
| Atualizações           | Dependabot semanal para npm, GitHub Actions e as três imagens base. Correções e minor entram automaticamente; major de Node, TypeScript, `@types/node` e Postgres e a linha mainline do nginx são decisões manuais, porque cada uma tem um motivo registrado acima | —                                                                         |
| Repositório            | Alertas do Dependabot, correções automáticas de segurança, detecção de segredos com bloqueio de push e relato privado de vulnerabilidades ativados no GitHub                                                                                                       | Painel de segurança do repositório; nenhum alerta aberto                  |
| Código                 | CodeQL (suíte estendida) analisando o TypeScript e os workflows do Actions                                                                                                                                                                                         | Primeira análise sem nenhum alerta                                        |

**Advisory transitivo numa ferramenta de desenvolvimento.** O `drizzle-kit` depende de `@esbuild-kit/core-utils`, que fixa o esbuild 0.18, afetado por um advisory moderado do servidor de desenvolvimento ([GHSA-67mh-4wv8-2f99](https://github.com/advisories/GHSA-67mh-4wv8-2f99)). A correção sugerida pelo `npm audit fix --force` era voltar o `drizzle-kit` para a 0.18, de 2023. Em vez disso, um `overrides` no `package.json` raiz troca o esbuild desse pacote pela 0.28.2, a versão que já estava na árvore. Todas as migrations do projeto foram geradas com o override aplicado, sem nenhum problema.

### Imagens Docker

O `npm audit` limpo não dizia nada sobre as imagens. Ao escaneá-las com o Docker Scout, nenhuma estava limpa, e nenhum problema vinha das dependências do projeto:

| Imagem     | Antes         | Depois      | O que mudou                                                                                                                                                                  |
| ---------- | ------------- | ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Backend    | 0C 4H 8M 1L   | 0C 0H 0M 0L | O runtime só executa `node`. Removi npm, npx, corepack e yarn, que vêm na imagem base com dependências próprias vulneráveis (`undici`, `brace-expansion`...)                 |
| Frontend   | 1C 2H 5M 5L   | 0C 0H 0M 0L | `apk upgrade` (corrige o `brotli`, que era a crítica) e remoção de `curl` e dos módulos `xslt`/`njs` do nginx, que puxavam `libxml2` e não são carregados                    |
| PostgreSQL | 5C 32H 29M 7L | 0C 1H 5M 5L | Imagem própria em [`docker/postgres`](docker/postgres/Dockerfile): sem `gosu`, sem `curl`, sem `libcurl`, rodando como usuário `postgres`, porta publicada só em `127.0.0.1` |

Detalhes que aprendi no caminho:

- **Apagar um arquivo numa camada nova não o remove da imagem.** Depois de deletar o `gosu`, o scanner continuava acusando-o, e com razão: o binário seguia dentro da camada da imagem base, só escondido. A imagem do Postgres agora copia o sistema de arquivos final para uma imagem vazia (`FROM scratch`), o que elimina o binário de fato.
- **O `libcurl` era usado só pelo `libpq-oauth`**, o módulo de OAuth do lado cliente que chegou no PostgreSQL 18. A API conecta com senha, então removi os dois. Em vez de apagar arquivos e deixar o banco de pacotes do Alpine inconsistente, o Dockerfile recria o pacote virtual de dependências do Postgres sem o `libcurl` e falha o build se ele continuar instalado.
- A variante Debian da imagem oficial era pior que a Alpine (4C 33H 30M 55L), por isso mantive Alpine.

### Riscos aceitos

Dois itens continuam aparecendo no Docker Scout. Nenhum tem correção publicada para o Alpine 3.24, e o Trivy, que usa a base de segurança oficial do Alpine, não acusa nenhuma vulnerabilidade nas três imagens.

| Pacote                                                                  | Situação                                                                     | Por que aceitei                                                                           | Mitigação                                                                                                                                                       |
| ----------------------------------------------------------------------- | ---------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `libxml2` 2.13.9-r2 no PostgreSQL (1H 5M 5L)                            | Sem correção publicada                                                       | É ligado ao binário do Postgres; removê-lo exigiria compilar o Postgres sem suporte a XML | O banco não é exposto à rede (só `127.0.0.1` e a rede interna do Compose) e a aplicação não usa funções XML. Explorar exigiria já poder executar SQL arbitrário |

## Dificuldades encontradas

**O lint de arquitetura não verificava pacotes npm.** Escrevi a regra "algoritmos não importam `fastify`" e ela passava em silêncio. Criei arquivos com violações de propósito e confirmei que só as dependências locais eram checadas. A causa estava no código do plugin: pacotes externos só são avaliados com a opção `checkAllOrigins: true`, que o README não menciona. Desde então, toda regra nova de fronteira é testada com uma violação proposital antes de ser considerada pronta.

**O CLI do shadcn instalou um pacote npm desconhecido.** Ao gerar o `Button`, o CLI não encontrou o alias `@/shared/lib/cn`, porque eu tinha declarado os `paths` só no `tsconfig.app.json`. Ele tratou `cn` como nome de pacote, adicionou `cn@0.5.0` às dependências e criou o arquivo numa pasta chamada literalmente `@`. Removi o pacote, conferi o lockfile e repeti os `paths` no `frontend/tsconfig.json`, que é onde o CLI procura. A lição é revisar o diff de qualquer código e dependência gerados por ferramenta.

**Os headers de segurança sumiam no nginx.** No primeiro teste em container, a CSP e o `X-Frame-Options` não apareciam nas respostas do front. Um `add_header Cache-Control` dentro de `location` faz o nginx ignorar todos os `add_header` do bloco `server`. Troquei o cache para a diretiva `expires`, que não tem esse efeito colateral.

**Uma expectativa errada sobre CORS.** Escrevi um teste esperando que uma origem não autorizada não recebesse `Access-Control-Allow-Origin`. Com origem fixa, o `@fastify/cors` sempre devolve a origem configurada, e o navegador bloqueia porque ela não bate com a de quem pediu. O comportamento estava certo; o teste foi corrigido para verificar que a API nunca reflete uma origem arbitrária.

**O teste de concorrência do refresh token passava sem o lock.** O teste dispara 20 renovações simultâneas com o mesmo token e espera exatamente uma sessão nova. Removi o `FOR UPDATE` de propósito, para confirmar que o teste quebrava, e ele continuou passando. A primeira requisição reaproveitava a conexão deixada aberta pelo login e terminava a transação inteira antes de as outras 19 concluírem o handshake com o PostgreSQL, então nunca havia disputa. Com o pool aquecido antes do disparo, tirar o lock faz um único token gerar 10 sessões, e o teste falha como deveria. Desde então, todo teste de concorrência é validado com a proteção removida.

**POST sem corpo chega como `null`.** O front renova a sessão com um POST vazio, porque o token vai no cookie. Declarei o corpo do `/auth/refresh` como opcional e mesmo assim recebia 400: o Fastify entrega `null`, não `undefined`, quando a requisição não tem corpo. O schema passou a aceitar os dois.

## Uso de IA

Usei o Claude Code como par de programação: para gerar a estrutura inicial, código repetitivo e testes, e para revisar. As decisões de arquitetura, de segurança e de versões são minhas e estão justificadas aqui e nos ADRs. Revisei cada arquivo antes de commitar e validei o comportamento com testes e com o ambiente rodando em Docker a partir de um clone limpo.
